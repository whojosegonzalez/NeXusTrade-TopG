## 5. Findings and limitations

No defect against the accepted contract was found. Every overflow failed closed: the budget was never exceeded, every refusal was reported truthfully, and no limited or missing evidence was reported as complete with exit 0. The points below are limitations for the operator-limit review. None was changed.

- **F1: the outstanding limit counts hand-off envelopes, not requests.** The owner reserves a slot for every accepted notification before the ledger knows whether it is a duplicate. Five notifications delivered in one tick end the run with `PROCESSING_OVERFLOW:OUTSTANDING_LIMIT`, even if they are duplicates that need no request (OC22). The `ws` client is configured with synchronous events, so frames read together can arrive in one tick. Delivered one at a time, the same duplicates do not overflow. The plan's `maxOutstandingRetrievals` field and the earlier runbook wording ("at most 4 outstanding" retrievals) described this as a retrieval limit. The runbook now states what is counted.
- **F2: retention covers what reached the recorder.** A frame that the wrapper or the `ws` client refuses (oversized frame or control payload) never reaches the collector or recorder. Retention can then read `COMPLETE` and re-derivation `REPRODUCED`. The refusal is visible only in `transport-diagnostics.json` (`refusedPayloadLimit`, `control.refused`) and in the owner's terminal cause. The run is `FAILED` with exit 3, so the CLI does not report success (OC25, OC26).
- **F3: drain expiry stops waiting for in-flight work.** When the drain deadline passes, the owner settles without waiting for the cut request. The sealed session ledger shows that request with no completion time, and its record stays `PENDING`. Retention reports `EXCHANGE_MISSING` and `PENDING_WORK:accountSettlementsPending`, and the run fails (OC23).
- **F4: practical capacity.** Retrievals are serialized and paced at 2,500 ms, and the limit counts envelopes, so a run can finish cleanly only on a quiet pool. That means at most 8 distinct swaps in the 60 s window (a ninth stops the session) and never a fifth envelope while four are unsettled. A busy pool ends in exit 3 with truthful, sealed evidence, never in excess requests.
- **F5: duplicate details.** Only 4 duplicate details are kept per signature. The fifth duplicate makes retention `INCOMPLETE` (exit 2), not a failure.
- **F6: the 16-control-frame limit only binds in an unclean run.** A clean run sees at most 4 server pings and 2 matched pongs (6 frames). Reaching 17 needs unsolicited pongs, which already make the run unclean.
- **F7: lifetime allowance for acquisition sealing.** Acquisition plus its local sealing and verification must finish within 20,000 ms of session open. With a fast acquisition that leaves 17,500 ms for sealing. With an acquisition near its 15,000 ms duration, only the 5,000 ms margin remains. Past that, the run is refused at the stage boundary before any connection.
- **F8: existing sanitizer limitation.** Credentials transformed by another encoding inside a payload (base64, hex, compression) are not detected (sanitizer header). OC29 covers literal, escaped, URL and binary forms only.
- **F9: rehearsal limits.** The fake `ws` client delivers whole buffers. Fragmentation, the `ws` receiver itself, TLS, real provider timing and the `logsSubscribe` filter semantics were not exercised. Sealing time on this machine is not a bound for another one.

## 6. Recommendation

**Retain the proposed limits for a first single capture.** Every limit held at its boundary, and every overflow ended the run truthfully with intact, bound evidence and no excess request. Revising the limits would not remove F1–F4. Those come from the accepted owner design (no retrieval queue, envelope-counted slots), and changing that design is outside Step 4. If the operator wants to observe a busier pool, that needs a revised owner design and a new review, not larger numbers in this profile. The operator should choose a pool expected to have fewer than 8 swaps per minute. Approval of the limits remains the operator's decision (Step 5).

**Public inputs still missing for a future capture** (none is selected here):

1. The exact Raydium CPMM pool address and its candidate mint. Both must be canonical base58, must differ, and the pool must be expected to be quiet enough (F4).
2. A new run id that does not exist under either evidence root.
3. Explicitly configured `SOLANA_RPC_URL` (https) and `SOLANA_WS_URL` (wss) from a provider that serves `logsSubscribe` and `getTransaction`. They are never derived and never printed.
4. The operator's approval of this profile (or a revised one), the time window and the exact live command. None is written yet.
